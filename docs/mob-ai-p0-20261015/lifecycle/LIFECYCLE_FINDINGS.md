## 本轮结果

已追出真实 CreateActor 请求、服务端 owner、原生角色登记、客户端重放、延迟 Despawn / Destroy、角色索引注销及独立服务端 owner 清理链。补上 RunAITask 的静态回调注册依据；复核真实服务端扣血与客户端重放的不同调用点。**这些是原版完整角色的静态链，尚未证明能创建适合 MC 生物的安全兼容代理，P0 整体仍未通过。**

## 真实创建链

| 阶段 | 静态证据 | 当前可以确认的事实 |
| --- | --- | --- |
| RPC包装 | `ServerRequest_CreateActor` native exec `2760E30`，注册指针 `5E9C6A8` | 解包角色TableID、位置/旋转、player/cheat/playerId、事件/出生点/possess等字段，经验证虚函数再调用实现槽`+15B8` |
| 真实实现 | NetworkPlayerController构造`2765F90 → E29A8B0`写vtable`5CC6798`；`+15B8 = 23B8550` | 不是调试空函数；从`1B43A40`取得请求对象并填写字段，交给`1AF3930` |
| 传送/队列 | `1AF3930` | 依当前游戏网络模式走RPC或本地队列，涉及锁和请求所有权移交；不能拿一次调用返回当作角色已存在 |
| 请求执行 | Create请求vtable`5C06328`的`+8 = 1B09750` | 依模式和player/cheat等标志分支；普通事件生成还会走`1C1C9A0`，其中一条完整角色路径调用`1AD1290`。不能假定所有参数组合相同 |
| 服务端owner | `1AD1290` | 查角色TableID配置、取得server manager，分配owner后调用`1BA6D20`初始化；成功后插入其自身`+170`登记表并继续初始化、广播。失败释放分支也存在 |
| 原生角色 | 非player分支`1BA73BF → 1CA9100` | 以角色表配置创建角色，建立资源/行为等配套；不是为现有StaticMesh补一个GUID |
| 统一登记 | `1CA98F5 → 1AAC240 → 1AAC500` | 角色登记到manager的GUID映射、ControlGUID映射与`+28/+30`角色数组；这正是上轮原生索敌读取的候选来源 |
| 客户端创建重放 | `23B8710 → 1B5D770`、packet vtable`5BF9E30`的`+8 = 1B196E0` | 客户端重放也调用`1AAC240`；创建请求、服务端owner和客户端镜像不能混成同一个对象或同一个GUID来源 |

`1AAC240`会先查既有GUID，缺失时分配；还可设置原生玩家索引。登记函数的参数与生命周期不能由SDK名称或少数寄存器推断完整。本次**没有**选择某个原版敌人/NPC的TableID替代MC生物，也没有构造/伪造GUID或试调这些函数。

原版完整创建路径会带入角色表、引擎角色、资源与行为初始化。对于MC生物，还缺“既可被原生攻击、又不另行成为一只自主SB角色”的已验证配置、行为与伤害隔离；单纯找到CreateActor并不能满足这个要求。

## 延迟移除与两套登记

1. `ClientBroadcast_DespawnActor` native exec `27606A0`调用虚函数`+1598`；NetworkPlayerController该槽是`23B8840`。它检查网络模式、分配客户端重放packet并排队，不能当成服务端owner删除入口。
2. `1B62C50`是跳转到`B8E15F0`的池分配入口；分配体写packet vtable`5BF9DB8`，其`+8 = 1B19CC0`。重放按GUID查询原生角色，找到后调用`1A70A80`。
3. `1A70A80`只设置相关标记，并在角色未处于Despawn/Destroy时把GUID去重加入manager`+1D8`数组；**此时没有同步从角色表注销或释放对象**。
4. manager更新`1AABEA0`末尾调用`1AAF5D0`消费队列。它调用`1A85000(actor,4)`进入Despawn，再依原版条件选择退场Show或`1A85000(actor,5)`进入Destroy，最后清空待处理队列。SDK枚举核对：4=Despawn、5=Destroy；不能强行跳过原版条件。
5. `1AAC8C0`是角色数组按索引移除路径：清理关联、地址映射`+48`、GUID映射`+98`、ControlGUID映射`+188`，调用`1C82DA0(actor+10)`，压缩数组并重算本地玩家索引。manager世界清理`1AAB870`同样逐个调用它。
6. **服务端owner是另一个对象和表。**它在server owner manager的`+170`表中，生产伤害桥通过`1AD6AB0`查到。不能只清角色数组，就假定服务端技能、效果和仇恨也已清理。
7. owner manager的`1AD57A0`扫描`+170`表；按owner虚函数/标志选择保留或清理。被清理时发原版移除通知、调用owner的`+10`清理虚函数并释放，之后重建保留表。已核对当前owner vtable`5C0BEE0`的`+10 = 1B9F670`、`+B8 = 1BA6D00`；清理前缀会清`+491`状态、关联角色`+60`和多个容器。
8. `1BA6D00`会转发至原生角色接口`+B8`，后者`1A6DE30`还检查其他状态/关联。**不能将它简化为“lifeState==5便可立即释放”**；完整保留条件、异步Show/效果结束和跨图先后顺序还需认证。

这轮明确了“双表移除”的必要性并找到了原版各自的清理路径；尚未证明可独立创建/注销MC兼容代理时所有回调都按这个先后顺序完成。不能直接调用数组删除函数、手动改lifeState或清owner指针作为生产方案。

## RunAITask 回调注册：已补齐静态关联

上轮只定位到类型ID读口和相邻回调，本轮增加了实际注册证据：

- 回调对象vtable`5BF6D68`的`+8`为`1ABF6F0`（类型ID），`+10`为`1ABF700`（处理函数）。
- 静态构造片段`6E8130..6E8181`分配对象、写入此vtable并交给`2267960`登记。
- `2267960`把对象加入静态列表；`2267A00`遍历该列表，通过`+8`取类型ID建立索引。

因此“回调只是相邻函数、未找到登记”的静态缺口已缩小。实际队列消费线程、World销毁时回调注销/停机的完整上下文仍缺，不能因此把原版异步任务入口认证为可从任意线程直接调用。

## 真正受害者、服务端伤害与重放

本轮只复核已有原生伤害链，没有扩展现有Eve保护hook：

1. `ApplyStatExecute` `1BA8720`通过当前owner的`+60`取得受害原生角色；源effect关联和来源owner仍应精确验证，raw source key不等于敌人GUID。
2. 服务端实际调用`1BA881E → 1A64CE0`，返回点为`1BA8823`；客户端重放调用`1B1F826 → 1A64CE0`，返回点为`1B1F82B`。它们调用同一个stat函数，但**不能两边都发布MC伤害**。
3. effect实例创建路径分别写受害owner`+58`和来源owner`+60`，项目现有`hit_source`会逐级验证effect、目标owner、来源owner、原生角色身份与地址；这可作为后续Mob专用通道的已有证据，不能放开到任意来源。
4. 当前`native_player_damage.intercept`限定唯一watched地址、原生玩家GUID、type=100、时效、调用点和允许线程，且共享`CombatHit`只有playerGuid，没有Mob UUID/代次。新Mob通道必须有自己的目标表和事件，**不能删掉type=100或watched条件来借用现有玩家通道**。
5. 当前Mesh没有原生owner/角色登记，因此不会自然进入上述真实伤害链。只有先认证合法战斗代理及源/目标关联，才可能在一次真正原生命中后安全转发给MC服务端；锁定、动画、广播和距离仍不等于伤害。
